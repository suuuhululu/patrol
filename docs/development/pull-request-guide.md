# PR 가이드

PR(Pull Request)은 작업 브랜치의 변경을 검토받고 `main`에 반영하기 위한 요청이다. 이 문서는 팀 운영 규칙이며 GitHub 보호 설정이 실제 적용되었다는 뜻은 아니다.

## 승인 담당

| PR 작성자 | 승인 담당 |
| --- | --- |
| 일반 팀원 | PM 또는 통합 관리자 `@jonnykoh2008-ship-it` |
| PM | 통합 관리자 `@jonnykoh2008-ship-it` |
| 통합 관리자 `@jonnykoh2008-ship-it` | PM |

- 작성자 외 승인 담당 1명 이상의 승인을 받는다.
- PM의 GitHub 계정은 실제 설정 적용 시 확인한다. 저장소 소유자와 동일하다고 임의로 가정하지 않는다.
- 인터페이스 등 여러 영역에 영향을 주면 해당 담당자에게도 검토를 요청한다.
- 승인자가 부재하면 PR을 유지하고 대체 승인 담당을 팀에서 정한다. 본인 승인으로 대체하지 않는다.
- PR 작성자는 자기 PR을 승인할 수 없다. [GitHub 공식 안내](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/approving-a-pull-request-with-required-reviews)

## 생성 절차

빈 저장소의 최초 문서 업로드로 `main`을 생성한 이후에는 다음 PR 절차를 따른다.

1. [브랜치 사용 가이드](branch-guide.md)에 따라 작업하고 커밋한다.
2. `git status`와 커밋 차이를 확인하여 필요한 파일만 포함했는지 검토한다.
3. `git push -u origin <작업-브랜치>`로 해당 브랜치를 업로드한다.
4. GitHub에서 base는 `main`, compare는 작업 브랜치로 선택한다.
5. 제목과 본문을 작성하고 승인 담당자를 리뷰어로 지정한다.
6. 작업 중이면 Draft PR로 두고, 검토 준비가 끝나면 리뷰를 요청한다.
7. 리뷰 수정은 같은 브랜치에 커밋·푸시하여 PR에 반영한다.
8. 검증·승인·대화 해결 후 PM 또는 통합 관리자가 Squash merge한다.
9. 병합 완료를 확인한 뒤 원격 작업 브랜치를 삭제한다.

Squash merge는 작업 중의 여러 커밋을 `main`의 한 커밋으로 묶는다. PR은 하나의 목적에 집중하도록 작성한다.

## 제목과 본문

제목 예: `docs(system): 브랜치 사용 가이드 추가`.

```markdown
## 변경 목적
변경이 필요한 이유

## 변경 내용
주요 수정 사항

## 검증 결과
실행한 검사와 결과, 실행하지 못한 검증과 이유

## 영향
영향받는 PC·패키지·인터페이스, 장비 검증 여부

## 관련 이슈
있는 경우에만 작성
```

## 검토 기준

| 변경 종류 | 확인할 내용 |
| --- | --- |
| Markdown | 내용 정확성, 링크, 명령 예시, 기존 설계와의 일관성 |
| ROS 코드 | 관련 패키지 빌드·테스트, 실패 및 복구 동작 |
| 인터페이스 | 발행·구독 측 호환성, 필드·단위·QoS, 문서 동기화 |
| 로봇 설정 | 대상 로봇 식별, 다른 PC에 미치는 영향, 필요한 장비 검증 |

검사 명령은 실제 패키지와 CI가 구성된 뒤 확정한다. 아직 없는 검사나 미실행 검증을 통과로 기록하지 않는다. 승인 뒤 의미 있는 변경이 추가되면 재검토를 요청한다.

## main 보호 적용 목표

- PR을 통한 병합, 작성자 외 승인 1명 이상, 미해결 리뷰 대화 해소.
- 코드 변경 후 기존 승인을 무효화하여 재승인 요구.
- 실제로 구성하고 정상 실행을 확인한 CI 검사만 필수 검사로 지정.
- 강제 푸시·브랜치 삭제 제한, 관리자 우회 최소화.

현재는 개인 무료 계정이고 저장소 공개 여부·관리자 권한·기능 적용 가능 여부를 확인하지 않았다. 설정 적용 전에 이를 확인해야 한다. 또한 승인 수 설정만으로 지정된 두 사람의 승인만 인정되는 것은 아니므로, 지정 승인자 강제 방식도 별도 확인한다. 문서 작성으로 보호가 활성화되지는 않는다.
