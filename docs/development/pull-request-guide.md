# PR 가이드 — 다른 PC와 통신할 때 확인받는 방법

## 1. PR은 왜 필요한가요?

PR(Pull Request)은 **“제가 이렇게 바꾸려고 합니다. 다른 팀의 프로그램과 함께 사용해도 되는지 확인해 주세요”**라는 변경 검토 요청이다.

PC끼리 통신할 때는 같은 약속을 사용해야 한다. 이 약속을 **인터페이스**라고 부른다. 메시지를 보낼 주소(토픽), 메시지 종류, 항목 이름, 숫자의 단위, 보내는 주기 등이 포함된다.

예를 들어 한 PC는 배터리를 `0.8`로 보내는데 다른 PC가 `80`을 예상하면 잘못 해석할 수 있다. 이 숫자는 설명용 예시이며 실제 계약 변경안이 아니다. **Git에서 파일 충돌이 없더라도 통신은 실패할 수 있다.** PR에서 변경 전후와 상대 팀의 영향을 확인하는 이유다. PR 자체가 통신 오류를 자동으로 찾아 고쳐 주지는 않는다.

## 2. 우리 프로젝트에서 지킬 약속

- **관제:** 별도 노드에서 명령과 제어 판단을 담당한다.
- **시스템 모니터:** UI로 상태·결과를 표시한다. 제어 명령을 발행하지 않는다.
- **공용 메시지:** `patrol_interfaces`를 사용한다.
- **설계 기준:** 최신 PM 결정과 System design의 확정 내용을 따른다. 과거 문서가 미정이라고 적었다고 확정된 규칙을 다시 바꾸지 않는다.
- AMR1·AMR2는 공통 코드를 사용하므로 한쪽 수정이 두 로봇에 미치는 영향을 확인한다.
- 같은 PC 3에서 실행되는 관제와 모니터도 기능이 다르면 각각 확인한다.

토픽·필드·자료형·단위·주기·응답 방식 중 하나라도 바꾸거나, 다른 팀이 받는 데이터의 의미가 달라지면 PR에 반드시 적는다. 상대 팀의 코드를 임의로 고치지 말고 해당 담당자에게 요청한다.

## 3. PR을 만드는 순서

1. [브랜치 사용 가이드](branch-guide.md)에 따라 작업 브랜치를 만든다. 예: `interfaces/update-message-contract`.
2. 먼저 System design과 [현재 인터페이스 문서](../interfaces.md)를 확인한다. 기존 코드가 확정 규칙과 다르면 코드를 규칙에 맞추는 변경이라고 적는다.
3. **아직 합의되지 않은 통신 규칙 변경은 문서 제안부터** 올린다. Draft PR(아직 검토·작업 중인 PR)을 활용하고, 코드 변경 범위 승인 후 구현한다.
4. 변경 파일을 커밋하고 작업 브랜치를 GitHub에 푸시한다.
5. GitHub의 **Pull requests → New pull request**를 누른다.
6. **base는 `main`**, **compare는 내 작업 브랜치**를 선택한다.
7. 아래 양식으로 제목과 본문을 작성한다. Reviewers에서 **PM과 통합 관리자 `jonnykoh2008-ship-it`**를 선택한다. 작성자 본인은 제외한다. 관련 상대 팀 담당자도 추가한다.
8. **Create pull request**를 누른다. 검토할 사람을 지정할 수 없다면 본문이나 댓글에서 `@`를 입력하고 실제 GitHub 계정을 선택해 알린다.

제목은 무엇이 달라지는지 보이게 쓴다. 예: **“[인터페이스 확인] AMR 상태 메시지를 확정 설계에 맞춤”**.

## 4. PM과 통합 관리자에게 남길 메모

아래 양식을 PR 본문에 복사하고 빈칸을 채운다. ‘확인 부탁드립니다’만 쓰지 말고 **누가, 어디를, 어떻게 바꿔야 하는지** 적는다. 아직 정하지 못한 내용은 추측하지 말고 ‘확인 필요’라고 쓴다.

```markdown
## 무엇이 문제인가요?
- 보내는 PC·기능:
- 받는 PC·기능:
- 현재 문제와 확인한 결과:

## 어떤 규칙을 따라야 하나요?
- System design의 절·링크 또는 최신 결정:
- 종류: 확정 규칙에 맞추는 수정 / 새로운 규칙 변경 제안
- 변경 전 → 변경 후: 토픽·메시지 타입·필드·자료형·단위·주기 중 달라지는 항목

## 누가 무엇을 바꿔야 하나요?
| 대상 PC·기능 | 파일 경로 또는 기능 이름 | 필요한 변경 | 담당자 | 현재 상태 |
| --- | --- | --- | --- | --- |
| 보내는 쪽 | | | | 요청 / 작업 중 / 반영 완료 |
| 받는 쪽 | | | | 요청 / 작업 중 / 반영 완료 |
| 공용 메시지·문서 | | | | 요청 / 작업 중 / 반영 완료 |

## 어디까지 수정했나요?
- 이 PR에 실제로 들어 있는 수정:
- 상대 팀에 요청할 수정과 관련 PR·수정 요청서 링크:
- 변경이 필요 없는 팀과 그 이유:

## 함께 적용할 때 주의할 점
- 이전 버전과 통신 가능한가요?: 가능 / 불가능 / 확인 필요
- 적용 순서와 동시에 바꿔야 하는 PC:
- 실패하면 복구할 버전과 방법:

## 어떻게 확인했나요?
- 보낸 예제 데이터 → 받아야 할 결과:
- 실제 결과와 로그·영상·커밋 링크:
- 아직 시험하지 못한 내용:

## PM·통합 관리자에게 요청
- PM: 담당자·적용 일정·변경 범위를 확인해 주세요.
- 통합 관리자: 송신·수신 규칙과 적용 순서가 맞는지 확인해 주세요.
- 상대 팀: 필요한 수정과 반영 상태를 확인해 주세요.
```

공용 규칙이나 다른 개발 단위의 수정이 필요한 경우에는 [수정 요청서](../change_requests/README.md)도 작성하고 위 본문에 링크한다. **PR은 변경을 검토·병합하는 곳**, **수정 요청서는 팀별 반영 상태를 남기는 기록**이다. 긴 내용을 두 곳에 복사하지 말고 PR에는 핵심과 요청서 링크를 적는다.

## 5. 메모 작성 예시

다음은 실제 오류 보고가 아닌 **작성 방법 예시**다. 파일이 아직 없다면 존재하는 파일처럼 쓰지 말고 ‘작성 예정’이라고 표시한다.

> **문제:** AMR과 관제가 서로 다른 메시지 패키지 이름을 사용하면 상태 메시지를 연결할 수 없습니다.
>
> **기준:** PM 확정 명칭은 `patrol_interfaces`입니다. 새 규칙을 제안하는 것이 아니라 기존 기준에 맞추는 작업입니다.
>
> **이 PR:** `docs/interfaces.md`의 패키지 표기를 확인·수정합니다. 실행 코드는 포함하지 않습니다.
>
> **AMR1·AMR2 담당자:** `src/patrol_amr/` 안의 메시지 import와 패키지 의존성을 확인해 주세요. 다른 이름을 사용하는 코드가 있다면 실제 파일 경로와 수정할 줄을 PR 댓글에 적어 주세요.
>
> **관제 담당자:** `src/patrol_control/`의 수신 메시지 타입과 의존성을 같은 기준으로 확인해 주세요.
>
> **모니터 담당자:** UI 데이터 수신부에서도 해당 타입을 직접 사용하는지 확인해 주세요. 사용하지 않는다면 ‘변경 불필요’와 이유를 남겨 주세요.
>
> **적용:** 코드 변경이 필요하면 각 담당자가 별도 PR을 연결하고, 함께 사용할 커밋을 정한 뒤 빌드·재시작합니다. 한 PC만 바꿔서 통신이 끊기는 상황을 방지해야 합니다.
>
> **검증:** 현재는 문서 확인만 완료했습니다. 실제 메시지 송수신은 아직 시험하지 않았습니다.
>
> **검토 요청:** PM은 담당 범위를, `@jonnykoh2008-ship-it`은 메시지 타입과 적용 순서를 확인해 주세요.

## 6. 수정 요청을 받으면 어떻게 하나요?

**내용을 고칠 때:** 같은 작업 브랜치에서 파일 수정 → 커밋 → 푸시한다. 새 PR을 만들지 않아도 기존 PR에 수정 내용이 추가된다. 본문도 최종 변경 내용에 맞춰 고친다.

**파일의 특정 부분을 지적할 때:** PR의 **Files changed**에서 해당 줄 옆의 `+`를 눌러 댓글을 남긴다. ‘틀렸습니다’ 대신 다음처럼 적는다.

```text
대상: [실제 파일 경로와 줄 번호]
현재: [현재 이름·값·동작]
수정 요청: [바꿔야 할 이름·값·동작]
근거: [System design의 해당 절 또는 확정 결정]
영향: [함께 수정하거나 확인할 PC·기능]
완료 확인: [어떤 입력과 결과로 확인할지]
```

수정한 사람은 ‘수정 완료’만 쓰지 말고 **수정 커밋과 확인 결과**를 답글로 남긴다. 상대 팀 코드 변경은 그 담당자가 진행한다. 합의 이후 내용이 달라지면 다시 검토를 요청한다.

## 7. 언제 main에 합치나요?

- 보내는 쪽과 받는 쪽이 같은 규칙을 사용함을 확인한다.
- 상대 팀의 변경 필요 여부와 적용 순서가 정리되어 있다.
- 문서 PR은 문서·링크를, 코드 PR은 해당 빌드·시험 결과를 확인한다. 통신 시험을 못 했다면 미실행이라고 표시하고 후속 시험을 정한다.
- 일반 팀원 PR은 PM 또는 통합 관리자 중 작성자 외 1명 이상이 승인한다. **PM이 작성했으면 통합 관리자, 통합 관리자가 작성했으면 PM**이 승인한다. 두 사람에게 검토를 요청하는 것과 두 사람 모두의 승인을 필수로 요구하는 것은 다르다.
- 검토가 끝나면 PM 또는 통합 관리자가 **Squash and merge**로 합친다. 여러 작업 커밋을 하나로 묶는 방식이다.

**PR 병합은 다른 PC의 자동 업데이트가 아니다.** 합의한 시간에 각 PC가 최신 코드를 받고 필요한 빌드·재시작을 해야 한다. 실제 연결 시험까지 확인해야 ‘통합 완료’다. 이 가이드는 팀 절차이며 GitHub가 자동으로 병합을 차단하도록 설정되었다는 뜻은 아니다.
