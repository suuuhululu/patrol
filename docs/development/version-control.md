# 버전 관리 가이드

이 문서는 `suuuhululu/patrol`의 코드와 Markdown 문서를 함께 관리하는 팀 규칙이다. 문서 생성 자체는 GitHub 설정 적용이나 커밋·푸시를 의미하지 않는다.

## 프로젝트 기준

- 환경: Ubuntu 24.04, ROS 2 Jazzy, Python 3.12. Docker는 사용하지 않는다.
- 실행 PC: AMR1, AMR2, 통합 관제·시스템 모니터, 비전의 총 4대.
- AMR1·AMR2는 공통 코드를 사용하고 로봇별 설정과 네임스페이스를 분리한다.
- 저장소는 하나로 유지하고 각 PC에서 별도로 clone하여 개발한다.
- `main`은 리뷰와 검증을 통과한 공통 기준본이다.

## 저장·커밋·푸시의 차이

| 동작 | 결과 |
| --- | --- |
| 파일 저장 | 현재 PC의 파일만 변경된다. |
| `git add <파일>` | 다음 커밋에 포함할 변경을 선택한다. |
| `git commit` | 현재 PC에 변경 이력을 남긴다. |
| `git push` | 커밋을 GitHub에 업로드한다. |
| PR 병합 | 검토된 작업을 `main`에 반영한다. |

2026-09-07 사용자 요청에 따라 기존 설계 문서와 가이드 4개의 최초 업로드를 진행한다. 이후 변경은 작업 브랜치와 PR 절차를 따른다. 아래 명령은 사용 예시다.

## 문서 관리 원칙

- 전체 시스템 문서는 `docs/`, 패키지별 사용법은 해당 패키지의 `README.md`에 둔다.
- 기준 문서는 고정 파일명을 사용한다. `최종`, `최종2`, `v3` 같은 복사본 대신 커밋 이력을 활용한다.
- 날짜별 회의록과 정식 제출본은 날짜를 붙여 각각 보존할 수 있다.
- 코드 변경에 따른 사용법·인터페이스 변경은 같은 PR에서 수정한다.
- 주요 설계 결정은 향후 `docs/decisions/`에 배경·결정·영향을 기록한다.
- 기존 작성 중인 문서는 경로를 유지한다. 이동이 필요하면 내용 변경과 분리한 PR에서 처리한다.
- Markdown 내부 문서 링크는 상대 경로를 사용한다.

## 변경 선택과 이력 확인

저장소 루트에서 실행한다. 아래 경로는 실제 대상 파일로 바꾼다.

```bash
git status --short
git diff -- docs/development/version-control.md
git add docs/development/version-control.md
git diff --cached
git commit -m "docs(system): 버전 관리 가이드 추가"
```

`git diff`에는 아직 추적되지 않은 새 파일 내용이 표시되지 않는다. 새 파일은 직접 읽고, 추가한 뒤 `git diff --cached`로 검토한다. 이미 스테이징된 다른 파일도 커밋에 포함되므로 전체 목록을 확인한다. 임시 산출물이 함께 추가될 수 있는 `git add .`보다 파일별 추가를 권장한다.

```bash
git log --oneline -- docs/development/version-control.md
git log -p -- docs/development/version-control.md
```

커밋 메시지는 `<type>(<scope>): <설명>` 형식을 권장한다. 예: `fix(control): 토큰 만료 시 정지 처리 수정`.

## 제외 대상과 복구

- `build/`, `install/`, `log/`, 캐시, 개인 가상환경, 작업용 임시 폴더는 Git 관리에서 제외한다.
- 비밀번호·인증 토큰·실제 접속 비밀정보는 커밋하지 않는다. 필요한 설정은 값이 비어 있는 예제 파일로 제공한다.
- 녹화 영상, DB, 대형 모델은 별도 보관하고 버전·다운로드 위치를 문서화한다.
- `.gitignore` 추가만으로 이미 추적 중인 파일이 제외되지는 않는다.
- 공유된 잘못된 커밋은 원칙적으로 되돌림 커밋을 만드는 `git revert`로 복구하고 PR을 거친다.
- 변경을 버리는 명령이나 강제 푸시를 복구의 기본 방법으로 사용하지 않는다.

## 배포 버전

`main` 병합과 실제 장비 검증 완료를 구분한다. 장비 검증을 마친 커밋에는 `v0.1.0` 형태의 릴리스 태그를 붙이고, 각 PC의 커밋·설정·검증 결과를 배포 기록에 남긴다. 배포와 롤백은 기록된 버전을 기준으로 수행한다.
