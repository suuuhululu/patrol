## 변경 이유

구조화 command/mission ID, 중복 충돌 비교 필드, 24시간과 1,000개 보관
규칙은 AMR parser·영속 저장소에 반영할 수 있다. 반면 확정된 명령 우선순위를
실행 중인 Nav2 goal에 적용하려면 기존 명령을 취소할지, 대기열의 낮은 우선순위
명령을 폐기할지, 각 명령의 CommandCheck와 PatrolReport를 어떤 상태로 끝낼지
추가 계약이 필요하다. 이를 임의로 정하면 관제 재전송과 AMR checkpoint가 서로
다르게 해석될 수 있다.

## 변경 전 → 변경 후

확정되어 AMR에 반영한 내용:

- command ID와 mission ID를 구조화 문자열로 검증한다. ID를 제어 입력으로
  파싱하지 않고 별도 `robot_id`·`command` 필드로 동작한다.
- 같은 command ID의 충돌 fingerprint는 `robot_id`, `command`, `target_id`,
  `target_pose`, `parameters_json`, `mission_id`만 사용한다.
- command ID는 24시간 이내 전부와 24시간이 지난 항목 중 최신 1,000개를
  영속 보관한다.
- 우선순위 값은 STOP → MOVE_TO_SAFE_ZONE → DOCK → CANCEL →
  RESUME_PATROL → START_PATROL이다.

구현 전에 결정이 필요한 내용:

1. 낮은 우선순위 명령이 **실행 중**일 때 높은 우선순위 명령이 도착하면 현재
   Nav2 goal을 즉시 취소하고 교체하는지, 현재 명령 종료 뒤 실행하는지.
2. 낮은 우선순위 명령이 **대기 중**일 때 높은 우선순위 명령이 도착하면 기존
   대기 명령을 유지·재정렬·취소 중 어느 방식으로 처리하는지.
3. 우선순위로 중단된 기존 command의 최종 PatrolReport를 CANCELED로
   발행할 때 사용할 reason code와 reason 문자열.
4. CANCEL command 자체의 PatrolReport와 CANCEL 대상 command/mission의
   PatrolReport를 각각 어떤 result로 생성하고 서로 어떻게 연결하는지.
5. CommandCheck의 ACCEPTED·EXECUTING·REJECTED 정수 매핑과 거부 reason
   code. 같은 ID 재전송 때 기존 check/report를 재전달하는 세부 경로.
6. STOP/CANCEL에도 `mission_id`를 항상 필수로 하는지, 특정 command만
   취소할 때 빈 mission ID를 허용하는지.

위 1~6은 제안값을 코드에 넣지 않고 계약 결정을 요청한다.

## 영향과 적용 순서

관제와 AMR이 1~6을 합의해 `interfaces.md`와 `amr.md`에 기록한 뒤,
AMR은 우선순위 queue와 preemption, CommandCheck publisher, 기존 report
재전달을 순서대로 구현한다. 혼합 버전에서는 현재처럼 실행 중 추가 주행 명령을
BUSY로 거부하며 STOP/CANCEL만 취소 신호를 보낸다. 실패 시
`safety_path_ready=false`로 주행을 차단하고 자동 재출발하지 않는다.
